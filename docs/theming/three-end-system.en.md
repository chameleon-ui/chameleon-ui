# How the Three-End System Works

> **English · [简体中文](three-end-system.md) · [繁體中文（香港）](three-end-system.zh-HK.md) · [العربية](three-end-system.ar.md)**

"Three-end" means Chameleon UI uses **the same set of components** to automatically adapt to **three device forms** — phone (390), tablet (768), desktop (1280) — rather than writing each form separately. This document explains the **real mechanism**.

> Companion: token compilation is covered in [`token-system.md`](./token-system.en.md); building a theme in [`creating-a-theme.md`](./creating-a-theme.en.md).

---

## 0. First, clarify a concept: React / Vue vs. "three-end"

Before discussing three-end, we must clarify the "framework" dimension to avoid confusing two different "ends":

- **Framework dimension = React, Vue** (the two render-adapter layers). See the next section.
- **Viewport/form dimension = phone, tablet, desktop (three-end)**. This is what "three-end" means.

The two are orthogonal: React and Vue **each implement three-end**. So "three-end" is not exclusive to any framework — it is a common capability of the design system.

### Why separate React and Vue?

Because the underlying **headless core (Ark UI / Zag) is packaged per framework** and cannot share interfaces across frameworks:

| | React line | Vue line |
| :--- | :--- | :--- |
| headless core | `@ark-ui/react` → `primitives` | `@ark-ui/vue` → `primitives-vue` |
| component shells | `components` (`*.tsx`) | `components-vue` (`*.vue`) |
| consumer umbrellas | `@chameleon-ui/react` | `@chameleon-ui/vue` |

But the two lines **share the same design layer**, so they are not "two random libraries" but "**one design system × two render adapters**":

- **Single catalog**: `components/catalog.json` (103 components) is the only authority; Vue has **no catalog of its own**.
- **Same contracts**: `contract.json` is shared by React and Vue (a `Button`'s props/a11y/RTL behavior is identical).
- **Same tokens / i18n / themes**: `tokens`, `i18n` (21 languages), `themes` are shared by both.

Conclusion: **design decisions live in the shared L1 (token/contract/i18n) layer; React/Vue only "translate" the same semantics into each framework's components.** This is the foundation of "cross-framework consistency", and why we split React/Vue rather than building just one.

## 1. Three-end = three breakpoint levels

The physical basis is three **breakpoint tokens** (defined in `packages/tokens/src/core/breakpoint.json`):

| Level | Token | Value | Range |
| :--- | :--- | :--- | :--- |
| mobile | `breakpoint.mobile` | `0px` | `< 768px` |
| tablet | `breakpoint.tablet` | `48rem` | `768 – 1279px` |
| desktop | `breakpoint.desktop` | `80rem` | `≥ 1280px` |

Breakpoints use **rem** (not px) so they follow the root font-size and zoom without distortion. This is the origin of the `390 / 768 / 1280` numbers (@16px root).

---

## 2. The core mechanism: container queries (`@container`) over `@media`

Traditional approaches use `@media (min-width: 1280px)` keyed to the **viewport**. Chameleon UI uses **container queries**: a component looks at the width of **its own container**, not the whole browser viewport.

```
component's own width =  < 20rem    → phone form
                         48–80rem   → tablet form (collapsible rail)
                        ≥ 80rem     → desktop form (persistent sidebar)
```

**Why container queries?**
- A component should morph by its **own available width** — embedded in a narrow sidebar vs. filling a wide viewport — not by the browser window.
- For example `Navigation` (see §4) uses `@container navigation (min-width: …)` to judge its container width to decide sidebar / collapsible / Tab.

**Gate guarantee**: component CSS **must not consume `@media` width breakpoints directly** (stylelint `chameleon/no-breakpoint-literal` blocks it); width response always goes through `@container` — so the mechanism cannot be bypassed and stays consistent.

## 3. Density and controls change per end

The three ends differ not only in **layout** but in **density**: the same component is more spacious on phone (touch-friendly) and more compact on desktop.

### 3.1 Density tokens (`density.json`)

| Token | Factor |
| :--- | :--- |
| `density.compact` | `0.875` |
| `density.standard` | `1` |
| `density.comfortable` | `1.125` |

Control minimum heights: `control.size.{compact,standard,comfortable}` = `2.25 / 2.5 / 2.75rem` (i.e. 36 / 40 / 44px @16px root). `touch-target.min` = `2.75rem` (44px, the accessibility floor for touch).

### 3.2 Default density per end

`@chameleon-ui/tokens/density.css` (generated by `scripts/density-css.mjs`) provides a **breakpoint-dependent default density**:

| End | Default density |
| :--- | :--- |
| mobile | `comfortable` (spacious, 44px touch target) |
| tablet | `standard` |
| desktop | `compact` |

**Two channels**:
- **Viewport level**: `@media` covers the page-level shell (the whole page changes density with window width).
- **Container level**: `@container app-shell` covers "a narrow shell embedded in a wide viewport" (e.g. a small panel inside a dashboard) — the `A5.3` scenario.
- **Explicit override**: `<html data-density="compact|standard|comfortable">` forces a level regardless of breakpoints.

**Important**: an app consuming `@chameleon-ui/tokens/css` **must also `import '@chameleon-ui/tokens/density.css'`**, otherwise `--cu-density-active` / `--cu-control-size-active` won't switch by breakpoint.

## 4. Three-end navigation: one API, three forms

The app shell (`AppShell`) and navigation (`Navigation`) are the most vivid demonstration — **the same `items` data renders three forms at three widths**:

| End | Navigation form |
| :--- | :--- |
| Phone (narrow container) | bottom **Tab Bar** (compact), overflow into `More` |
| Tablet | **collapsible rail** |
| Desktop (wide container) | **persistent sidebar** |

Implementation: `Navigation`'s CSS uses container queries to switch form by `min-width: 48rem / 80rem`:

```css
@container navigation (min-width: 80rem) { /* sidebar form */ }
@container navigation (min-width: 48rem)  { /* rail form */ }
@container navigation (max-width: 20rem)  { /* Tab form */ }
```

Companion three-end components: `AppShell` (three-end app skeleton) · `SafeArea` (notch / gesture-bar insets) · `ActionSheet` (phone bottom action panel) · `Navbar` / `NavigationBar` (horizontal stacked navigation).

---

## 5. Workflow: why "one codebase, three forms" doesn't blow up

- **Styles**: a single component's styles write the three levels with container queries; CSS custom properties (`--cu-*`) carry the token values.
- **JS/logic**: the same component API (`items`, `locale`, props) — the form switch is pure CSS and does not change the data structure.
- **Contracts**: `contract.json` records `responsive` and three-end behavior, shared by React and Vue.

So "three-end" is not three implementations but **one contract + one interaction logic + container-query styles**, morphing automatically at three widths.

---

## 6. Quick self-check

1. Three-end switch not working?
   - Confirm `@chameleon-ui/tokens/density.css` is imported (see 3.2).
   - Confirm stylelint didn't reject a `@media` width breakpoint (should be `@container`).
2. A component embedded in a narrow container not shrinking?
   - The container it depends on needs `container-type: inline-size` (e.g. the Navigation container, AppShell).
3. `data-density` not applying?
   - `density.css` not imported, or `[data-density]` spelling doesn't match `compact|standard|comfortable`.
